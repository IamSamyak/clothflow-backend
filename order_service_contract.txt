## Order Service current architecture

Order Service owns:

* Orders
* Order items
* Order status history
* Order-side inventory reservation records

It does NOT access Product or Inventory databases directly.

Communication:

Order Service
|
+---- HTTP ----> Product Service
|
+---- HTTP ----> Inventory Service

Product information is copied into `OrderItem` as a snapshot:

* productId
* sku
* productName
* unitPrice
* quantity
* subtotal

## Important Hibernate/transaction issue already fixed

We encountered:

`LazyInitializationException` for `Order.statusHistory`.

Cause:

* `@Transactional` methods were being called from the same `OrderService`
* Spring self-invocation bypassed the transactional proxy
* LAZY collections were accessed without an active Hibernate session

We fixed this by moving transactional state-changing operations into:

`OrderStatePersistenceService`

Do NOT solve this by:

* changing LAZY to EAGER
* enabling Open Session in View

Keep:

```yaml
spring:
  jpa:
    open-in-view: false
```

We then encountered the same issue with:

`Order.items`

The correct fix was to create:

`OrderReadService`

This service owns transactional reads and response mapping.

OrderService delegates:

```java
return orderReadService.getOrder(orderId);
```

and:

```java
return orderReadService.getOrder(orderId, customerId);
```

This ensures `Order.items` is initialized inside a real transaction.

## Important distributed-systems caveat

The current implementation is intentionally a synchronous baseline.

Example:

```text
Order has 3 items

Inventory commit item A -> success
Inventory commit item B -> success
Inventory commit item C -> timeout
```

The system can have partial progress.

Stable reservation IDs make retries safer because Inventory operations are idempotent.

Later we must solve this properly using:

* Kafka
* Transactional Outbox
* Saga
* retries
* dead-letter/failure handling
* event-driven state transitions

Do NOT pretend the current synchronous workflow is a distributed transaction.
